02 · Tecnología

Stack tecnológico completo

El sistema está compuesto por 7 servicios containerizados con Docker Compose, cada uno con health checks y restart automático. Un solo comando — docker-compose up -d — levanta toda la plataforma en segundos.

El backend está separado en dos microservicios independientes: Auth Service en el puerto 3001 (solo autenticación y JWT) y el Backend principal en el 3000 (lógica de negocio, pedidos, pagos). Este diseño permite escalar, mantener y proteger cada pieza de forma aislada.

06 · Autenticación

JWT doble token + bcrypt — stateless y seguro

Login exitoso — se generan 2 tokens independientes
Access Token
Duración: 15 minutos
Payload: userId · storeId · role
Firma: HMAC-SHA256
Storage: en memoria del cliente (nunca localStorage)
Refresh Token
Duración: 7 días
Storage: HASH en BD (nunca plaintext)
Rotación: nuevo par en cada renovación
Revocable individualmente o en masa
// Cada query siempre filtra por store del JWT const payload = jwt.verify(token, JWT_SECRET); req.user = { userId: payload.userId, storeId: payload.storeId, // NUNCA del body role: payload.role };
Rate Limiting Auth

5 intentos / 15 min / IP + email. Bloqueo temporal de 15 minutos al superar el límite.

RBAC — 4 roles

superadmin · vendor · staff · customer — verificado en cada endpoint antes de ejecutar el controlador.

N

El sistema es stateless — el servidor no guarda sesiones en memoria. El storeId viaja dentro del JWT firmado, lo que garantiza que aunque un vendedor intercepte la petición de otro, no pueda ver sus datos.

07 · Seguridad

Modelo STRIDE — 6 amenazas, 6 controles

S — Spoofing
Suplantación de identidad
JWT HMAC-SHA256 · bcrypt salt=12 · Refresh tokens almacenados como HASH, nunca en texto plano.
T — Tampering
Manipulación de datos
Joi valida 100% de los endpoints · Sequelize usa queries parametrizadas — imposible SQL injection.
R — Repudiation
Repudio de acciones
Winston logs JSON con correlationId único por request · tabla activity_log con IP y user agent.
I — Information Disclosure
Fuga de información
Helmet.js: HSTS · CSP · X-Frame-Options · CORS whitelist · aislamiento multi-tenant total.
D — Denial of Service
Denegación de servicio
Rate limiting en Nginx + Express · health checks en todos los containers · restart automático Docker.
E — Elevation of Privilege
Escalada de privilegios
RBAC en middleware authorize.js · store_id solo desde JWT firmado — nunca del request.
Controles preventivos aplicados

bcrypt salt=12 · HSTS habilitado · CORS whitelist · Nonce anti-replay en pagos · UUIDs no enumerables · CHECK stock ≥ 0 en BD · RBAC 4 roles · Joi en cada endpoint

Controles detectivos y correctivos

Winston JSON logs · Tabla audit_log inmutable · Alerta ERR-C06 al admin en discrepancias · Revocación de tokens por sesión o global · Suspensión de cuentas desde panel SuperAdmin

N

El modelo STRIDE no fue solo documentación — cada amenaza tiene su control implementado en código. Por ejemplo, el nonce único en pagos previene que alguien replaye una transacción antigua para "pagar" una orden nueva sin enviar ETH real.

# demand_analyzer.py — weighted moving average weights = [i + 1 for i in range(n)] # días recientes pesan más: [1,2,3,...,30] weighted_avg = sum(sales[i] * weights[i] for i in range(n)) / sum(weights) trend = "up" if second_half > first_half * 1.1 else "down" if second_half < first_half * 0.9 else "flat"

El motor de IA no depende de OpenAI ni de ningún servicio externo de pago — esto es clave. Los algoritmos son propios, escritos en Python puro, lo que significa costo cero por consulta y sin riesgo de que cambien los precios o la API externa.

Decisiones críticas de diseño
1
PostgreSQL en lugar de MongoDB
ACID: el descuento de stock y la creación de orden son una transacción atómica. Si falla, todo hace rollback.
2
UUIDs en lugar de auto-increment
No se pueden enumerar ni adivinar IDs ajenos. Con IDs secuenciales (1,2,3) es trivial probar todos los recursos.
3
Snapshot de precio en order_item
El precio puede cambiar después. La orden siempre refleja exactamente lo que el cliente pagó en ese momento.
4
CHECK stock ≥ 0 a nivel de BD
Restricción en PostgreSQL — imposible inventario negativo, ni con queries directas, ni con bugs de código.
-- Restricción crítica — nivel base de datos ALTER TABLE product_variant ADD CONSTRAINT stock_non_negative CHECK (stock >= 0);
N

El hecho de que el stock nunca pueda ser negativo no es solo una validación en código — está enforced a nivel de base de datos con un CHECK constraint. Aunque haya un bug en la aplicación o alguien inyecte una query, PostgreSQL lo rechaza.

11 · Preguntas del evaluador

Respuestas clave preparadas

¿Cómo previenen que un vendedor vea datos de otro?
Triple capa: JWT firmado contiene storeId, middleware authenticate.js lo extrae, y cada query incluye WHERE store_id = req.user.storeId. Aunque manipulen el HTTP, el storeId viene del token firmado.
¿Qué pasa si el motor de IA falla?
Graceful degradation: aiService.js tiene try-catch con timeout 5-8s. Si no responde, retorna objeto vacío. El usuario no ve la predicción pero puede seguir comprando y vendiendo normalmente sin ninguna interrupción.
¿Cómo garantizan que un pago ETH sea real y no falsificado?
Verificación on-chain con ethers.js via RPC: wallet destino = wallet del vendedor, monto ≥ solicitado, mínimo 3 bloques de confirmación. Es imposible falsificar sin controlar la blockchain pública de Ethereum.
¿Por qué bcrypt y no SHA-256?
SHA-256 es veloz por diseño (para integridad, no contraseñas). bcrypt es intencionalmente lento, tiene salt aleatorio (anti rainbow-tables) y cost factor ajustable conforme crece el hardware. Salt=12 hace que cada intento tarde ~250ms — fuerza bruta inviable.
¿Por qué PostgreSQL y no MongoDB?
ACID es crítico aquí: el descuento de stock y la creación de la orden son una transacción atómica. Si falla cualquier parte, todo hace rollback. La eventual consistency de MongoDB no es aceptable para operaciones financieras.
¿Qué es el rate lock y por qué existe?
El ETH fluctúa constantemente. Al iniciar el pago, bloqueamos la tasa GTQ→ETH por 10 minutos. Si el cliente demora y el precio cambia, la solicitud expira y genera nueva tasa. Evita inconsistencias y arbitraje de precios.
